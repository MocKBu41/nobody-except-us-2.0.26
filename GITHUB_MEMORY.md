Главный файл поведения бота:

`BOT_MEMORY/BOT_LOGIC_CURRENT.json`

Он создан из присланной пользователем плиточной схемы `BOT_logic_editor.html` от **2026-09-14** и является **источником истины для поведения NEU BOT**.

Обязательное правило для любых будущих изменений поведения:

1. Сначала прочитать `BOT_MEMORY/BOT_LOGIC_CURRENT.json`.
2. Если пользователь меняет правило поведения, приоритет, условие, дистанцию, состав, покупку/вызов юнита или переход состояния — **обязательно внести это изменение в `BOT_MEMORY/BOT_LOGIC_CURRENT.json`**.
3. Затем синхронизировать код текущей версии бота с обновлённой логикой.
4. Если изменение ещё не проверено в игре — статус `НУЖЕН ТЕСТ`.
5. После теста прочитать новый лог из `/LOG/`, подтвердить/отклонить изменение и обновить память.

Подробное правило хранения находится также в `BOT_MEMORY/README.md`.

### Текущая каноническая стратегия BOT 2.0

- OPENING: последовательно `infantry -> recon -> tank -> mech_inf`.
- Экономика: 1200 BP на старте, +20 BP/сек, резерв 200 BP.
- Spawn retry: 2 сек; timeout: 60 сек.
- После OPENING состояние `EXPAND`.
- В EXPAND каждый живой отряд сохраняет собственную цель до захвата/исчезновения; новая цель выбирается среди незахваченных флагов с минимальной нагрузкой, при равенстве нейтральный флаг приоритетнее.
- `infantry` и `mech_inf` получают приказы раньше техники.
- `tank`, `recon`, `attack_heli` получают 10-секундную задержку следования.
- Потеря `recon`, `tank`, `mech_inf` или `attack_heli` после OPENING ставит бота в `WAIT_REINFORCEMENT`; замена может использовать резерв.
- При преимуществе по флагам >= 1 бот переходит в `DEFEND`; при потере преимущества возвращается в `EXPAND`.
- Если живой обычной infantry нет — вызывается замена.
- Вертолёт проверяется каждые 30 сек и может вызываться только при подтверждённом точном числе танков противника >= 3; одного boolean `EnemyHasTanks` недостаточно.
- Максимум 1 `attack_heli`.
- Артиллерия отключена.
- Unmatched/passenger squads не принимаются автоматически в боевую структуру бота.

### Не считать реализованным до отдельного подтверждения

- Высадка пехоты из БМП/БТР: `crew_emit` найден, но безопасный BotApi/Lua метод высадки только десанта не подтверждён.
- Пехотное развёртывание примерно за 100 м и фронт с интервалом 5–6 м.
- Остановка танка примерно в 50–100 м от точки.
- Остановка БМП/БТР примерно в 20–50 м от точки.
- Реальное координатное движение отрядов без проверенного coordinate bridge.

Старая наработка `bot.v1_22.logic.lua` умеет рассчитывать tank standoff 60–70 единиц и использовать `NEU_EngineMove`, но её геометрию нельзя слепо включать: анализ боя 7 показал, что определение карты только по одинаковым именам флагов (`f1..f11`) может выбрать неправильную карту. До надёжного runtime map ID координатная геометрия в BOT 2.0 отключена.

## История испытаний

Папка `/LOG/` используется как постоянная история логов испытаний бота.

При анализе нового боя или ошибки необходимо:

1. Проверить последний лог в `/LOG/`.
2. При необходимости сравнить его с предыдущими логами.
3. Проверить отчёты в `/LOG/reports/`.
4. Выделить новые ошибки и изменения поведения.
5. Использовать результаты предыдущих испытаний, а не анализировать каждый бой изолированно.
6. После исправления проверять по следующему логу, действительно ли проблема исчезла.

Последняя изученная база перед BOT 2.0: `BOT_GPT/v1_30_1`, созданная по результатам анализа `game7.log`.

## Карты и координаты

В проекте ведётся работа с координатами игровых карт GEM2.

Извлекаются и индексируются в том числе:
- `flag_point`
- `SpawnPoint`
- координаты маршрутов/точек движения

Координаты могут извлекаться из `battle_zones.mi`, расположенных в каталогах карт внутри `multiplayer_maps.pak`.

При разработке новых инструментов для точек использовать существующие рабочие скрипты индексации как основу (например, логику `_map_points_index` / `_flag_points_final`), а не создавать несовместимый формат без необходимости.

## Принцип работы с кодом

Перед правкой:

1. Прочитать `GITHUB_MEMORY.md`.
2. Если задача относится к поведению бота — прочитать `BOT_MEMORY/BOT_LOGIC_CURRENT.json`.
3. Найти текущую рабочую/тестовую версию нужной подсистемы.
4. Проверить связанные файлы и зависимости.
5. Для проблем поведения бота — прочитать последние подходящие логи из `/LOG/` и `/LOG/reports/`.
6. Сравнить предполагаемое изменение с уже работающей логикой.

После правки:

1. Не считать исправление подтверждённым только потому, что код выглядит корректно или загружается.
2. Если требуется проверка в игре — отметить изменение как `НУЖЕН ТЕСТ`.
3. После получения нового игрового лога подтвердить или отклонить гипотезу.
4. Зафиксировать важный результат в памяти проекта.
5. Любое изменение поведения бота обязательно отражать также в `BOT_MEMORY/BOT_LOGIC_CURRENT.json`.
