## Разработка бота

Основные рабочие версии бота находятся в `BOT_GPT` и связанных с ним каталогах/версиях репозитория.

Текущая линия разработки включает `v1_22` и последующие версии.

При изменениях бота необходимо сохранять уже работающую логику и вносить локальные изменения. Перед созданием новой версии сначала изучить предыдущую рабочую версию и последние логи.

### Требования к поведению, которые уже обсуждались

- Пехотные отряды должны двигаться к целям/флагам и уметь разворачиваться перед атакой.
- Пример текущей схемы: примерно за 100 м до точки пехота начинает развёртывание; бойцы наступают фронтом с интервалами порядка 5–6 м.
- Танки должны иметь собственную дистанцию остановки перед точкой, ориентировочно 50–100 м.
- БМП/БТР должны подходить ближе, ориентировочно 20–50 м, с последующей высадкой пехоты там, где это предусмотрено логикой.
- Бот должен уметь распределять силы по разным направлениям/флагам, а не собирать всё на одной цели.
- Вертолётная логика должна учитывать наличие бронетехники противника; ранее обсуждавшийся триггер — более двух единиц тяжёлой/танковой техники игрока.
- Для отладки нужна визуализация отрядов, целей и точек/линий движения.

Это требования/ориентиры разработки, а не доказательство того, что каждый пункт уже реализован в текущем коде. Фактическое состояние всегда проверять по коду и свежему логу.

## Карты и координаты

В проекте ведётся работа с координатами игровых карт GEM2.

Извлекаются и индексируются в том числе:

- `flag_point`
- `SpawnPoint`
- координаты маршрутов/точек движения

Координаты могут извлекаться из `battle_zones.mi`, расположенных в каталогах карт внутри `multiplayer_maps.pak`.

При разработке новых инструментов для точек использовать существующие рабочие скрипты индексации как основу (например, логику `_map_points_index` / `_flag_points_final`), а не создавать несовместимый формат без необходимости.

## Принцип работы с кодом

Перед правкой:

1. Прочитать `GITHUB_MEMORY.md`.
2. Найти текущую рабочую версию нужной подсистемы.
3. Проверить связанные файлы и зависимости.
4. Для проблем поведения бота — прочитать последние подходящие логи из `/LOG/`.
5. Сравнить предполагаемое изменение с уже работающей логикой.

После правки:

1. Не считать исправление подтверждённым только потому, что код компилируется/загружается.
2. Если требуется проверка в игре — отметить изменение как `НУЖЕН ТЕСТ`.
3. После получения нового игрового лога подтвердить или отклонить гипотезу.
4. Зафиксировать важный результат в памяти проекта.

## Статусы

Для проектных записей использовать понятные статусы:

- `РАБОТАЕТ` — подтверждено испытанием/логом.
- `НУЖЕН ТЕСТ` — реализовано, но ещё не подтверждено в игре.
