## Краткий вывод

Baseline v1.0.0 не строит БТГ и не ждёт формирования группы. После появления каждого squad бот практически сразу вызывает `CaptureFlag` и отправляет этот squad на выбранный флаг. Выбор флага в коде случайный и не использует рассчитанный `FlagPriority`; поэтому свои, нейтральные и вражеские флаги не образуют стратегическую последовательность.

Лог подтверждает именно модель `SpawnUnit -> OnGameSpawn -> CaptureFlag`.

За активную часть боя зарегистрировано:

- 36 `SpawnUnit`;
- 36 `OnGameSpawn`;
- 49 `CaptureFlag`;
- 36 первичных приказов сразу после `OnGameSpawn`;
- ещё 13 `CaptureFlag` без нового `OnGameSpawn`, то есть повторные/переназначенные приказы;
- 8 вхождений текста `Флаг захвачен` (одно сообщение встречается дважды в одной строке, поэтому это не обязательно 8 уникальных захватов);

## Что делает код v1.0.0

1. На `GameStart` читает доступные units для текущей армии.
2. На каждом `Quant` пытается покупать/спавнить подходящий по экономической формуле юнит.
3. Приоритет типа юнита зависит от `Income`, `EnemyHasTanks()` и количества своих/вражеских/нейтральных флагов.
4. После появления squad вызывается `setSquadOrder(captureFlag, squad, OrderRotationPeriod)`.
5. `captureFlag()` выбирает один из `BotApi.Scene.Flags` и вызывает `BotApi.Commands:CaptureFlag(squad, flag.name)`.
6. Стадий `assemble/rally/approach/attack`, связи пехоты с танком/БМП, дистанции до флага и индивидуального построения бойцов в v1.0.0 нет.

## Высадка / eLeave

В логе найдено 76 строк `Attempt add order eLeave to linked or inactive entity`:

- 36 для UKR;
- 40 для RUS.

Они возникают группами примерно в `00:02:14`, `00:02:19`, `00:02:22`, `00:02:23`, `00:02:26`, `00:02:39`, `00:02:51`, `00:03:14`, `00:03:19`, `00:03:21`, `00:04:17`.

Важное ограничение: сам `bot.lua` v1.0.0 НЕ вызывает `eLeave` и вообще не содержит явной команды высадки. Следовательно, эти `eLeave` инициируются внутренней обработкой игрового приказа/другим игровым скриптом. Это полезный след для исследования штатной высадки, но строка прямо сообщает, что конкретная попытка была дана linked/inactive actor и не была нормально принята.

Среди `eLeave` встречаются не только пассажиры, но и `tankman`, поэтому нельзя считать эти строки доказательством корректной управляемой высадки пехоты.

## Ошибки/аномалии, влияющие на поведение

Во время активной части боя найдено 122 строки `can't spawn entity` для 42 разных имён. Примеры:

- `mp2/ukr/tro_rpb`
- `mp2/ukr/%n2 ... %n9, %na)`
- `mp2/rus/3002 ... 3009`
- `mp2/rus/2a)`
- `mp2/rus/28`, `mp2/rus/29`

Также есть минимум 4 ошибки `Can't put armor ...`.

Это означает: общий squad может получить `OnGameSpawn`, но часть его внутренних entities/бойцов может не появиться. Поэтому для следующих тестов нельзя оценивать численность отряда только по факту успешного `SpawnUnit`/`OnGameSpawn`.

## Что лог НЕ даёт

Текущий debug показывает `CaptureFlag fN`, но не показывает:

- координаты squad во времени;
- фактический путь;
- дистанцию до флага;
- момент полной остановки;
- состав конкретного squad по entity ID;
- точную связь `SpawnUnit name -> squadId` для двух одновременно работающих AI во всех случаях;
- успешность конкретного `eLeave` как высадки.

Для этих данных следующая версия трассировки должна логировать `squadId + unit + position + target + passengers + order state` периодически и на каждом изменении приказа.

## Базовое правило для следующих версий

v1.0.0 сохраняется без изменений как контрольный baseline. Новая логика БТГ должна строиться как новая версия и сравниваться с этим отчётом: spawn -> assembly -> route -> approach -> dismount/standoff -> assault, а не подменять исходный baseline.
